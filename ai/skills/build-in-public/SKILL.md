# Build in Public

Turn verified development work into public stories that build Sean's audience
while attracting feedback that can improve the project. The repository remains
the factual source of truth.

The Git preference `build-in-public.status` controls automatic checkpoints,
not explicit requests to use this skill.

## Read first

Read relevant history, plans, documentation, reviews, tests, devlogs, and media.
Identify project maturity and private or security-sensitive boundaries. Ask for
personal observations only when necessary to tell the story honestly.

Never infer usage, reactions, metrics, hours, intent, or validation from commits
alone. It is valid to recommend not sharing when there is no useful story,
proof, or question.

## Frame one useful story

Choose one primary objective:

- **Audience:** demonstrate a distinctive lesson, capability, or point of view.
- **Feedback:** attract people qualified to reduce a specific uncertainty.
- **Both:** select one as primary so the call to action remains clear.

Center the story on a concrete change, decision, failure, surprise, or lesson.
Support it with proof such as a repository, demo, clip, screenshot, comparison,
test result, user observation, or measured outcome.

## Respect the publishing architecture

- Repository records are the private factual source.
- `newsletter.seanoliver.dev` is the canonical public home for substantial
  long-form stories and email distribution.
- `seanoliver.dev` is the identity and project hub: evergreen project pages,
  demos, selected excerpts, and newsletter signup.
- X, LinkedIn, and Reddit receive native adaptations, not identical cross-posts.

Publish a complete long-form story in one place. Prefer portable email
subscriptions and periodically export publication and subscriber data.

## Produce a sharing brief

By default, use `assets/sharing-brief-template.md`. Do not draft every post
unless asked. Include:

1. The source evidence and one central story.
2. The primary audience and objective.
3. The proof that makes the story credible.
4. Suitable channels, native angles, sequence, and timing rationale.
5. One focused call to action or feedback question per item.
6. Signals to capture and the project decision they could inform.

Any copy you draft goes under Sean's name, so **REQUIRED SUB-SKILL:** use `writing-as-sean`. Rule 12 applies hardest here: public posts are where metaphor and flourish feel most justified and read worst. Say the literal thing.

Read `references/channels.md` when selecting distribution. Browse current
first-party platform guidance before making time-sensitive claims, and read a
target community's live rules before recommending a Reddit submission.

Return substantive feedback to the project's decision, issue, research, or
devlog records with attribution. Popularity metrics are evidence, not automatic
product decisions.

## Authorization boundary

Creating a brief or draft does not authorize publishing, scheduling, replying,
subscribing anyone, or sending messages. Take an external action only when Sean
explicitly requests it and the final target and content are clear.

## Out of scope

- Do not create the automatic opt-in prompt; standing tool instructions own it.
- Do not replace a factual project devlog or manufacture missing evidence.
- Do not expose private repository details, credentials, unpublished security
  findings, employer work, or third-party information.
- Do not create artifacts during a checkpoint unless Sean accepts the offer.
